## Proposed minimal data flow

1. **Keep HTTP metrics as-is.** Local Prometheus-style inspection reuses the protected endpoint. If later scraped on AWS, design a private authenticated collector with explicit secret handling; no public scrape endpoint. Do not duplicate HTTP 202 latency under a new name.
2. **Async lifecycle (local implementation first):** events are `accepted`, `leased`, `attempt_failed`, `succeeded`, `failed`. An `accepted` event is attempted only for a *new* job after SQS send succeeds; if the first send fails and an idempotent retry sends the persisted pending job later, this best-effort event is missing rather than counted twice. Retry-aware durable acceptance needs a separately reviewed outbox/transition design. The **submit persist-and-send duration** of a recorded event spans first synthetic payload write through SQS send, measured with `time.monotonic_ns()` in the producer. Existing HTTP middleware independently measures client POST 202; an idempotent retry is never a new `accepted` job. Keep `created_at`/`completed_at` integer seconds and the existing TTL/API contract, but persist an additional `created_at_ms` at creation, capture `first_lease_at_ms` **after SQS receive but before** the first successful conditional lease write, and capture `terminal_at_ms` before a successful conditional terminal write. Neither timestamp is the commit time; failed writes do not emit completion events. Capturing lease time after the write would require a second conditional write or losing the lease timestamp on crash, so the local design intentionally uses pre-write time; **WorkerAttempt starts after the successful lease write and excludes its latency**. `first_lease_at_ms - created_at_ms` is *submission-to-first-lease*, including S3/DynamoDB/send/API/worker scheduling, **not** pure SQS residence. `terminal_at_ms - created_at_ms` is *submission-to-terminal*, not exact client POST-to-result (which needs the existing client benchmark). Worker execution per attempt uses monotonic start/end within that worker process; do not subtract timestamps from different machines for worker execution. Cross-process timestamps use UTC epoch milliseconds; negative results from clock skew are **unavailable**, never clamped to zero or published as latency. Use bounded `payload_read`, `payload_contract`, `inference`, `storage`, `other` failure classes; no exception text. A successful conditional DynamoDB update is the only source of terminal events; retries, conflicts and duplicate deliveries cannot count as new completions. A leased worker records `attempt_failed` best-effort after a processing exception even if the fallback DynamoDB state update fails; it must not emit `failed` unless that terminal update succeeds. This records an attempted worker error, not proof of a persisted retry/terminal transition. No fleet-wide pending/running gauge is inferred by scanning TTL items. No owner, job ID, HMAC, token, GPS, S3 path or raw URL in telemetry.
3. **Transport boundary and queue monitoring:** the API and bounded worker are separate processes; in-memory worker metrics cannot appear at the API's `/internal/metrics`, and worker restarts reset in-memory counts. Local tests inject a tiny in-memory event recorder (no AWS) to verify event meaning/cardinality; it is not a durable monitoring backend. Successful DynamoDB transitions and telemetry delivery are **not atomic**: a crash or delivery failure can lose an event after a job succeeds. Until a separate durability design exists, emission is best-effort and dashboards must show telemetry missing/stale rather than infer zero activity. Cloud-phase transport (review-only) may use privacy-scrubbed EMF in a restricted worker log group or scoped `PutMetricData`; neither is enabled locally, and EMF delivery/replay is not exactly-once. Prefer native SQS `ApproximateNumberOfMessagesVisible` / `NotVisible`, DLQ visible count and `ApproximateAgeOfOldestMessage` over custom polling. These are approximate/eventual; oldest-age can exclude poison messages that move behind healthy ones and cannot measure any single job's runtime. Dashboard proposal: protected HTTP metrics **only if a private collector is approved**, bounded async lifecycle and worker errors **only if cloud delivery is verified**, native queue depth/age and the existing DLQ alarm. No notification recipient or new IAM without review. EC2 stopped or missing telemetry means *unknown*, not zero errors.
4. **Synthetic drift replay:** use only two hardcoded fictional fixtures and two allowlisted model variants. Fix seed `20261017`; generate deterministic chronological event order per variant, with the first **100 events/variant** as reference and subsequent **disjoint 50-event/variant** windows. Four joint categories are `(HOME, OFFICE)` emitted/abstained pairs; smoothed category probability is `(count + 0.5) / (N + 2)`. Jensen–Shannon divergence in bits is `0.5 * KL₂(P‖M) + 0.5 * KL₂(Q‖M)`, `M=(P+Q)/2`, using the reference and each eligible window. Define abstention share exactly as `(HOME_abstained + OFFICE_abstained)/(2N)`; the shift is the absolute difference from reference. A window crosses the threshold when JS **>0.10 bits** or abstention shift **>=0.20**. Require two consecutive eligible crossing windows for a **simulated** alert; one normal or `<50`-event window resets the streak (the latter reports `insufficient_support`, never `normal`). Evaluate variants independently. Test unchanged, one-window spike then normal, sparse-reset, and two-window fixture-mix shift. Repeating two fixtures is not independent sampling; this demonstrates input-mix sensitivity only, not model degradation, statistical significance or real-world drift. Output fixed-order four-category aggregate counts for reference and each window (including sparse windows), per-variant/window statistics and `simulated_offline_replay`, no coordinates or account traces. No AWS drift alarm in the local phase.

## Privacy, delivery and cost gate

All replay inputs stay fictional and local. No new dependency is required for counts/JS (`collections`, `math` and `json` suffice). Prefer existing tests and bounded dimensions. Retain existing `/geolife/dev/api` CloudWatch log group's observed 7-day retention and the existing DLQ alarm; do not alter them in this phase. Before deployment, review the actual worker log sink, new metric publishing or private scrape path, least-privilege IAM, metric series count, dashboard ownership, log retention and teardown plan. Remove only newly approved Checkpoint 3 dashboard/alarms/collector on teardown; preserve S2b state, queue, DLQ and historical evidence.

**CloudWatch series/cardinality budget for review (not yet published):** The local `InMemoryRecorder` stores five validated lifecycle event types and a bounded attempt error class; it does **not** publish seven CloudWatch metrics or persist counters. The seven names below are a proposed event-to-series inventory, not observed measurements. `accepted` supplies Accepted/SubmitPersistAndSend (S3 write → DynamoDB write → SQS send, not client HTTP 202 ACK); `leased` supplies FirstLeaseWait only when clock-skew-safe; `attempt_failed` supplies AttemptFailed/WorkerAttempt; terminal `succeeded`/`failed` supply Terminal/TerminalDuration and WorkerAttempt only when their respective durations are available. Any real mapping, delivery and validation of dimensions is a separate cloud-phase implementation gate. No worker metrics appear on the API's existing `/internal/metrics` endpoint.

**Dimension allowance:** dimensions have *only* `model` (`cp2-v2-complete-link-200m`, `cp2-v2-dbscan-100m`); `outcome` (`succeeded`, `failed`) appears only on terminal counts. Error classes are aggregated into a single `attempt_failed` series per model, not dimensions. A metric identity is **metric name × full dimension tuple**; each additional dimension value adds a billed series. Workers retain no user/job/request/fixture dimensions.

## Acceptance and implementation sequence (requires review approval)

1. **Local RED contract tests:** event cardinality: same-key retry does not produce another `accepted`; conditional DynamoDB failure produces no `succeeded`/`failed` event; duplicate completed message does not repeat `Terminal`. Check millisecond/subsecond durations, pre-SQS receive wait exclusion from worker runtime, clock skew/negative cross-process durations marked unavailable and TTL seconds unchanged. Assert no sensitive/dynamic dimensions, preserved `/internal/metrics` authentication, and no accidental exposure of worker metrics through API. Test fixtures without real GPS or AWS network.
2. **Local implementation:** minimal injected recorder in API/worker transition points; successful conditional writes precede terminal events, with documented best-effort loss/crash window. Restarted worker has no durable in-memory counter; simulated telemetry emission failure cannot silently turn into a healthy `zero errors` signal or alter job state. Run targeted/dependent suite and CI checks; S2b response/auth/model behavior unchanged.
3. **Local drift runner/tests:** deterministic seed `20261017`, exact four-category JS and two-label abstention definition, per-variant chronological windows; unchanged, one-window spike then normal, sparse reset, and two-window fixture-mix shift. Output bounded sanitized `simulated_offline_replay` report; never label repeats as independent samples or real drift.
4. **Monitoring availability vs correctness:** native SQS metrics are approximate/eventual, not job counts; `ApproximateAgeOfOldestMessage` does not reliably characterize poison-message delay. Missing worker/API telemetry, worker restart or stopped EC2 is `unknown/stale`, not an observed error-free period. Cloud transport, collection success and signal freshness require separate AWS evidence before dashboard/alert acceptance.
5. **CloudWatch review gate (separate authorization):** review EMF/private log group versus scoped `PutMetricData`, enumerate the 16 potential series plus existing metrics, estimate actual regional cost/retention and teardown, and validate a saved Terraform plan *without applying*. Only after operator approval deploy, verify transport/freshness and run a synthetic alert/clear test; stop EC2 when that approved session ends.
