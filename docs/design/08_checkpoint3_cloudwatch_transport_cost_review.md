## Verified boundary and recommendation

- The existing `/internal/metrics` in `src/geolife/api/metrics.py` exports per-process protected HTTP metrics; it cannot scrape the bounded worker container. `AwsAsyncJobs._record()` calls an optional recorder and stores no durable metric; the committed local prototype attaches a JSON-lines EMF recorder only when `GEOLIFE_S2B_EMF_ENABLE=1`, with no CloudWatch SDK call. `worker_cli.py` runs a bounded process and prints only an aggregate poll count.
- The existing handoff `docs/deployment/08_aws_ssm_deployment_handoff.md` configures Docker `awslogs` **for the original API only**, to `/geolife/dev/api`; the worker examples do not use that driver. The original EC2 Terraform log group retains 7 days. The EC2 role's `GeoLifeDevCloudWatchWriter` inline policy permits log-stream creation/description and PutLogEvents only for the API log group; the S2b runtime policy provides S3/DynamoDB/SQS but no metric publishing permission. Existing S2b DLQ alarm observes `ApproximateNumberOfMessagesVisible` every 300 s and has **no notification actions**.
- **Recommend one dedicated restricted S2b telemetry log group with separate API and worker streams, Docker awslogs, and bounded EMF JSON to stdout for a future internal trial**, not the original API log group. `accepted`/`SubmitPersistAndSend` originate in the new S2b API container; lease/attempt/terminal events originate in the bounded worker. The local prototype explicitly enables the sink in **both** processes via `GEOLIFE_S2B_EMF_ENABLE=1`; Docker's log driver alone cannot create metrics. The proposed cloud transport still requires a separately approved group, scoped EC2-role writer permissions, a 7-day retention/cost review, and log-driver settings for **both** new S2b containers. Leave the original `geolife-api` and `/geolife/dev/api` unchanged. Local JSON serialization is not evidence of CloudWatch extraction.

Neither option provides exactly-once telemetry, guarantees worker-side event durability or makes production monitoring ready. Proposed delivery failure must be explicitly reported as telemetry unavailable/stale, never interpreted as zero worker errors. Without a live CloudWatch publisher, *all seven* names below are prospective series, not emitted data.

## Proposed metric inventory and dashboard

Only fixed `model` (`cp2-v2-complete-link-200m`, `cp2-v2-dbscan-100m`) and optional `outcome` (`succeeded`, `failed`) may become CloudWatch dimensions; error class stays in locally bounded diagnostics and is not a dimension. One metric identity is name × dimension tuple. `duration_ms=None` from clock skew is omitted, not published as zero; a leased event with no remaining metric produces no EMF line.

| Name (`GeoLife/SyntheticS2b`) | Unit | Dimensions | Max series | Source |
| --- | --- | --- | ---: | --- |
| `Accepted` | Count | model | 2 | New-job producer `accepted` after SQS send; can undercount first-send-failure/retry. |
| `SubmitPersistAndSend` | Milliseconds | model | 2 | Same producer event: S3 persist → DynamoDB persist → SQS send; **not** full HTTP 202 ACK. |
| `FirstLeaseWait` | Milliseconds | model | 2 | First worker lease after SQS receive; submission-to-first-lease, **not** pure SQS wait. Epoch-ms clocks can skew. |
| `WorkerAttempt` | Milliseconds | model | 2 | One monotonic sample per actual attempt: `attempt_failed` on processing failure, `succeeded` on terminal success; terminal `failed` emits no second worker sample. Excludes receive/lease write. |
| `AttemptFailed` | Count | model | 2 | Processing exception after lease, even if fallback state update fails; also a post-commit SQS ACK error (no worker-duration sample, no second terminal event); best-effort. |
| `Terminal` | Count | model, outcome | 4 | Successful conditional `succeeded`/`failed` update only; duplicate ACK is not another terminal event. |
| `TerminalDuration` | Milliseconds | model | 2 | Created-to-terminal UTC-ms duration after successful terminal write; not exact POST-to-GET latency. |
| **Total proposed** | | | **16** | Local opt-in EMF stdout prototype is tested; CloudWatch ingestion/extraction is **not implemented or verified**. |

The [review-only dashboard JSON](checkpoint3_s2b_dashboard_review.json) contains eight widgets and 25 metric rows (<50 references): 16 custom EMF series, five native `AWS/Logs` rows and four native `AWS/SQS` rows. It shows accepted/terminal counts by model/outcome, attempt failures, p95 durations (where samples suffice), source visible/not-visible depth, oldest source-message age and DLQ visible depth. Queue names `geolife-mle-s2b-dev-jobs` and `geolife-mle-s2b-dev-dlq` were verified against the isolated S2b Terraform root (`prefix` + resource names) and local private state outputs. The existing DLQ alarm state is a separate console check, not a dashboard widget; no new alarm is created. No new collector to scrape API HTTP histograms in this first cloud gate; show them only if a separately approved authenticated private scrape is built. Native SQS metrics are approximate/eventual and oldest age can skip poison messages. A bounded worker may exit with no new series; display stale/no-data separately from zero. A stopped EC2 is a *maintenance/offline* state, not an error-free signal.

**Alarm selection:** keep existing DLQ alarm unchanged; propose **zero** new alarms for initial trial. After observing transport/freshness and replay noise, consider at most one worker-attempt-failure or queue-age alarm with `treat_missing_data=missing`, a separate planned maintenance signal, and a review of low-volume false positives. Do not attach SNS/email or claim pager coverage without separate approval. Fictional offline drift alerts are local reports, not CloudWatch alerts.
